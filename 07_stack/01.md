# 01.asm - Basic push and pop
## What the program does
It puts 100 in RAX and 200 in RBX, pushes both onto the stack, then pops
them into RCX and RDX, and exits.

## Stack walkthrough
When the program started, RSP was `0x7fffffffdc50`.

| Step | Instruction | RSP | What happened |
|------|-------------|-----|---------------|
| 1 | `mov rax, 100` | 0x7fffffffdc50 | RAX = 0x64 (100) |
| 2 | `mov rbx, 200` | 0x7fffffffdc50 | RBX = 0xc8 (200) |
| 3 | `push rax` | 0x7fffffffdc48 | 100 stored on the stack |
| 4 | `push rbx` | 0x7fffffffdc40 | 200 stored on top of 100 |
| 5 | `pop rcx` | 0x7fffffffdc48 | RCX = 0xc8 (200) |
| 6 | `pop rdx` | 0x7fffffffdc50 | RDX = 0x64 (100) |
| 7 | exit syscall | 0x7fffffffdc50 | program ended normally |

## How the stack works here
The stack grows **downwards**, so every `push` makes RSP smaller. Each push
moves RSP down by 8 because registers are 64 bits (8 bytes). The value is
written at the new RSP address.

`pop` does the opposite. It reads the value at RSP, puts it in the register,
and then makes RSP bigger by 8.

The stack is **last in, first out**. I pushed 100 first and 200 second, so
200 was on top and came off first.

## Observations
- RSP went from `...dc50` to `...dc48` to `...dc40` on the two pushes. That
  is 8 bytes each time (0x50 - 0x48 = 8).
- RSP went back up to `...dc50` after the two pops, so the stack ended up
  balanced.
- RCX got 200 and RDX got 100. This is the reverse of the push order, which shows the stack is last in, first out.
- pop does not erase anything, it just moves RSP.
- RAX and RBX did not change when I pushed them. Push only copies the value.
- The program printed nothing and `echo $?` gave 0.
- gdb displays the instructions in AT&T style (`mov $0x64,%eax`) but it is
  the same as the `mov rax, 100` in my code.
