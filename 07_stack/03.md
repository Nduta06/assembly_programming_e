# 03.asm - Call and ret with a helper function

## What the program does
It puts 10 in RAX, calls a function called `calculate` that adds 5 to it,
and comes back to `after_call`, where RAX is 15. Then it exits.

## Stack walkthrough
When the program started, RSP was `0x7fffffffdc50`.

| Step | Instruction | RSP after | RAX after | What happened |
|------|-------------|-----------|-----------|---------------|
| 1 | `mov rax, 10` | 0x7fffffffdc50 | 0xa | stack not touched |
| 2 | `call calculate` | 0x7fffffffdc48 | 0xa | return address pushed |
| 3 | `add rax, 5` | 0x7fffffffdc48 | 0xf | RAX is now 15 |
| 4 | `ret` | 0x7fffffffdc50 | 0xf | return address popped, back at `after_call` |
| 5 | `nop` | 0x7fffffffdc50 | 0xf | RAX = 15 as the comment says |
| 6 | exit syscall | 0x7fffffffdc50 | 0x3c | RAX changed to 60 for the exit |

## How the stack works here
This program uses the stack without me writing `push` or `pop`. The `call`
instruction automatically pushes the address of the next instruction onto
the stack. The `ret` instruction automatically pops that address and jumps
to it. That is how the CPU knows where to go back to after the function.

There are no local variables, so there is no `rbp` or `sub rsp` here.

## Observations
- RSP only changed by 8: down on `call` (dc50 to dc48) and up on `ret` (dc48 to dc50).
- `ret` did not need any address from me. It took it from the top of the stack, and the program landed at `after_call`.
  `info symbol 0x40100a` said it is `after_call`.
- RAX was 0xf (15) at `after_call`, which matches the comment in the code.
- The program printed nothing and `echo $?` gave 0.
